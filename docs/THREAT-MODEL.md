# Модель угроз и соответствие методам обнаружения VPN

Исследование к ветке с улучшениями 1.6.x. Цель — честно сопоставить **опубликованные** методы
обнаружения средств обхода блокировок с тем, что реально измеряет NetworkChecker на Windows.

> **Статус источников.** Так называемая «Методика выявления признаков использования средств
> обхода блокировок на клиентских устройствах» (апрель 2026) распространена в виде утечки;
> её подлинность и юридический статус официально не подтверждены. Исследование RKS по 30 APK
> описывает конкретную выборку приложений и не является описанием алгоритмов всех площадок.
> Измерения ТСПУ привязаны к дате, оператору и региону. Всё ниже — **модель для самопроверки**,
> а не реконструкция решения РКН, оператора или сайта.
>
> Инструмент диагностический: он помогает владельцу машины понять, какие сведения видны
> локально и внешним сервисам. Он не даёт рекомендаций по сокрытию tunnelling и не измеряет
> «безопасность» подключения.

## 1. Три разных наблюдателя

Путаница чаще всего возникает из того, что «РКН определяет VPN» относят к одному механизму.
На деле это три независимых позиции наблюдения.

| Слой | Кто видит | Что доступно | Что может приложение на ПК |
|---|---|---|---|
| **① Сервер / площадка** | сайт, банк, маркетплейс, антифрод | IP клиента, GeoIP/ASN/hosting, репутация VPN/proxy/Tor, `X-Forwarded-For`/`Forwarded`/`Via`, RTT (SNITCH), пассивный TCP/IP fingerprint (MSS/TTL/окно), JA3/JA4, WebRTC/IPv6-утечки, язык и часовой пояс браузера, корреляция потоков | только **модель**: публичные GeoIP, эхо-заголовки собственного HTTP-зонда, системные локаль и часовой пояс |
| **② Устройство (мобильное)** | приложение с разрешениями Android/iOS | `NetworkCapabilities.TRANSPORT_VPN`, `VpnTransportInfo`, `dumpsys vpn_management`, `NEVPNManager`/`NWPathMonitor`, `CFNetworkCopySystemProxySettings`, `__SCOPED__`, utun/tap/ppp/ipsec, локальные SOCKS/HTTP-порты, список установленных приложений, logcat | **не применимо**: приложение работает на Windows; мобильных API и телеметрии других устройств нет |
| **③ Устройство (десктоп)** | локальный процесс с правами ОС | WinINET/WinHTTP/PAC/env-прокси, `GetAdaptersAddresses`, `Get-NetRoute`, `RasEnumConnection`, DNS/NRPT, MTU, hosts, реестр Uninstall, процессы/службы, файрвол kill switch | **основная зона покрытия** репозитория |
| **①′ ТСПУ / DPI оператора** | оборудование в канале | сборка потоков, сигнатуры протоколов (WireGuard/OpenVPN/IKEv2/L2TP/PPTP/Shadowsocks/VLESS...), SNI и QUIC Initial, TLS-параметры, энтропия, размеры/порядок/тайминги пакетов, поведенческая классификация, активное зондирование серверов, кэш классификации и списки IP | видны только **последствия**: RST, пауза в handshake, дросселирование, отсутствие ответа; причину установить нельзя |

По оценке утечки, порядок проверки — серверный слой → мобильные устройства → десктопы,
а решения принимаются не непрерывно, а при входе/авторизации/целевом действии; до 80%
клиентских проверок приходится на Android/iOS. В репозитории закрыты в основном слои ① (модель)
и ③, поэтому «серверные» и «клиентские» сигналы в отчёте разделены явно.

## 3. Матрица: метод → состояние в репозитории

Обозначения: **есть** — реализовано и отражено в отчёте; **частично** — моделируется или
наблюдается с оговорками; **нет** — локально недоступно в принципе или не реализовано.

### Серверный слой (①)

| Метод | Состояние | Где / комментарий |
|---|---|---|
| Внешний IP, консенсус источников | **есть** | `IpConsensusBuilder`, `IpComparisonCheck`; сравнение только внутри IPv4/IPv6 |
| GeoIP, страна, ASN, hosting, VPN/proxy/Tor-метки | **частично** | `GeoIpCheck`, «Глазами сайта»; публичные базы, не РАНР/MaxMind «до запуска», возможны ошибки |
| Репутация дата-центров, rDNS, DNSBL, Tor-exit списки | **нет** | закрытые/ip-листы на стороне площадки; `hosting` — единственный косвенный признак |
| `X-Forwarded-For` / `Forwarded` / `Via` | **частично** | `CdnPullingCheck` показывает заголовки **зонда приложения**, не браузера |
| SNITCH / аномалия edge-RTT | **частично** | `RttTriangulationCheck` (β) измеряет медианы с клиента, без географии пути |
| Расщепление адресов Web/UDP, корреляция потоков | **частично** | `IpConsensus.IsSplit`; netflow-корреляция оператора недоступна |
| DNS-утечка (whoami-имя vs адрес выхода) | **есть** (новое) | `TransportObservationCheck`, вес 0 |
| Подмена/расхождение системного DNS и DoH | **есть** (новое) | там же; без DNSSEC, «нет данных» ≠ «совпало» |
| WebRTC-, IPv6-, браузерные DNS-утечки | **нет** | нужен браузерный стек |
| JA3/JA4, ECH, пассивный MSS/TTL/окно, отпечаток браузера | **нет** | см. «Чего модуль не измеряет» в отчёте |
| Язык/часовой пояс браузера, GPS, MCC/PLMN | **нет** | в модели используются системные `CultureInfo`/`TimeZoneInfo`, что явно оговорено |

### ТСПУ / DPI (①′)

| Метод | Состояние | Где / комментарий |
|---|---|---|
| DNS → TCP → TLS: на каком шаге ломается | **есть** | `DomainReachabilityCheck`, без вывода о причине |
| SNI-триггер vs контрольный SNI | **есть** (новое) | `TransportObservationCheck`; сервер вправе отвергнуть чужое имя, а зонд отличается от браузера |
| UDP/443 QUIC-подобный датаграмм 1200 байт | **есть** (новое) | только факт ответа; у UDP нет обязательного ответа |
| ICMP/TCP-расхождение, RST, TTL | **частично** | `IcmpSpoofingCheck` (β), без доказательства инъекции |
| Сигнатуры протоколов, энтропия, размеры/тайминги, ML | **нет** | требует точки наблюдения в канале и датасета |
| Активное зондирование VPN-серверов, кэш классификации, списки IP | **нет** | сторона оператора |

### Клиентский слой, десктоп (③)

| Метод | Состояние | Где / комментарий |
|---|---|---|
| Прокси WinINET/WinHTTP/PAC/env | **есть** | `DirectSignsCheck`; PAC анализируется статически |
| Адаптеры, tun/tap/wg/utun/ppp, `IF_TYPE_PROP_VIRTUAL` | **есть** | `WindowsPlatformProbe`, `DirectSignsCheck` |
| Маршруты (default / host `/32`), `Get-NetRoute` | **есть** | `IndirectSignsCheck`, только IPv4 в текущей реализации |
| DNS, NRPT, MTU 1350/1400/1420, hosts | **есть** | `IndirectSignsCheck` |
| RAS/`Get-VpnConnection`, Uninstall-реестр, процессы, службы, kill switch | **есть** | `WindowsPlatformProbe`, `DirectSignsCheck` |
| Локальные SOCKS/HTTP-порты 1080/9000/5555/3128/8080/8888, Tor 9050/9051/9150, 16000–16100 | **есть** (расширено) | `BypassCheck` + `LocalPortScanner`: настройки, диапазоны, TCP LISTEN ОС, лимит и параллелизм |
| API клиентов (Xray 10085, Clash/`/version`) | **частично** | ответ ≠ идентификация клиента; gRPC Xray не реализован |
| Каталог современных клиентов/протоколов | **есть** (расширено) | `VpnClientCatalog`: AmneziaWG, Hysteria2, TUIC, Juicity, Mieru, NaiveProxy, Trojan, ShadowTLS/Cloak/obfs4, XHTTP/XTLS, WinDivert |
| Список приложений на **других** устройствах, logcat, серверные команды | **нет** | Windows-процесс не имеет такого доступа |

## 4. Что изменено в этой ветке

| Пункт | Изменение |
|---|---|
| **A** | этот документ: источники, три слоя, матрица «есть / частично / нет», оговорки об источниках |
| **B** | `LocalPortScanner` и `BypassCheck`: порты и диапазон методики, TCP LISTEN системы, ограничение `MaxLocalProxyPorts`, параллельные пробы; настройка диапазонов в UI |
| **C** | whoami-DNS (`DnsLeakTestDomains` больше не мёртвый список), сравнение системного DNS с публичным DoH, адрес выхода для сравнения; «нет данных» не считается чистым результатом |
| **D** | новый модуль `Транспорт и DPI (β)` с **весом 0**: UDP/443, TLS с контрольным и триггерным SNI, явный список того, что не измеряется (ECH/JA3/JA4/WebRTC) |
| **E** | `VpnClientCatalog` расширен; `FalsePositiveCatalog` добавляет контекст к находкам о виртуализации, корпоративном VPN и границе «роутер/VM» |
| **F** | `MethodologyMatrix`: чистая функция от собранных `CheckResult` и `IpConsensus`, раздел в Markdown/JSON, оговорки FP, список локально неизмеримого; тесты и справка |

Все новые сетевые наблюдения имеют вес 0 или являются контекстом к существующим находкам:
индекс 0–100 и правила `Detected` **не изменились**.

## 5. Ложные срабатывания (из методики и измерений)

Методика сама перечисляет причины ошибок; в коде они вынесены в `FalsePositiveCatalog` и
печатаются в матрице отчёта:

- корпоративный VPN, Always On VPN, антивирусный/родительский фильтр с локальным прокси;
- WSL2, Hyper-V, Docker Desktop, VirtualBox, VMware: виртуальные адаптеры, NAT, `/32`-маршруты;
- VPN, поднятый **на роутере** или в другой сети: внешние сервисы видят туннель, локальных следов нет;
- резидентные прокси, CDN/anycast, балансировка, ошибки GeoIP и репутационных баз;
- split tunneling: часть приложений идёт напрямую, DNS и HTTP могут выходить с разных адресов;
- новые VPN-сервисы и IP, которых ещё нет в базах; ICS и «раздача» интернета;
- поездка, роуминг, удалённый рабочий стол и VM: несовпадение языка/часового пояса и страны IP.

`MethodologyMatrix` поэтому не выдаёт вероятность: каждый сигнал имеет состояние
`есть` / `не найден` / `нет данных`, а итог формулируется как «по матрице», с явным указанием
неполноты данных и альтернативных объяснений.

## 6. Границы инструмента

1. **Не решение площадки.** Матрица — модель по уже собранным наблюдениям; реальные правила
   сайтов, белые списки и серверная телеметрия неизвестны.
2. **Не вероятность.** Индекс 0–100 — нормированная сумма весов; шкала «Глазами сайта» —
   другая, тоже условная эвристика. Ни одна из них не откалибрована.
3. **Отсутствие ≠ чисто.** Пропущенный/упавший модуль, отсутствие UDP-ответа и тишина после
   ClientHello не превращаются в «сигналов нет».
4. **Один сигнал не решает.** Совпадение серверного и клиентского сигналов в матрице всё равно
   сопровождается списком альтернативных объяснений.
5. **Windows only.** Мобильный слой (≈80% клиентских проверок в методике) недоступен; слой
   ТСПУ доступен только как последствия на конце соединения.
6. **Никакой инструкции по обходу.** Документ описывает наблюдаемость, а не способы скрыть
   туннель; активное зондирование чужих серверов приложение не выполняет.
